Warnings

      

      
The interpreter runs a subset of the compiler's warning
        analyses, so a program the compiler warns about can come back clean
        here. lupin reports these in its observation record, and at
        a terminal they stay there.

    


    

      
Observation record

      

      
The line lupin run - --json prints: the
        spec/06 observation record, which is the only thing the compiler and the
        interpreter compare through. A program that traps now carries what it
        printed before it died in stdout_inline. Through
        lupin 0.1.22 that field was null on every trapping program, so
        the two implementations were record-identical whatever they printed —
        and one real disagreement about what a trap does to a pending
        defer sat behind it, unmeasured, until 0.1.23.

    

  






  
What is running

  
lupin is the wolf reference interpreter. It is a separate
  implementation from the compiler, written against the specification, and the
  two share no code. The build in this page is that program, compiled to
  WebAssembly from the revision this site was built from. Nothing is uploaded:
  the source stays in the tab, and no request leaves the page after the module
  and the samples have loaded.


  
The revision of the specification it reads is the compiler's own, and at
  these pins it is not the compiler's newest. This interpreter, lupin
  __LUPIN_VERSION__, was built to __PIN_specrev_short__, which is
  a release tag and not a revision of the compiler's trunk — but it is the tag
  before the one install advertises,
  __COUNT_speccommits_word__ commits of the compiler's own history back. So the
  newest release whose text that revision carries whole is one release back,
  and that is what the pages are written against. The pin being a tag and the
  pin being current are different claims, and this is a pin where the first is
  true and the second is not: a week ago the pin was an untagged commit short
  of a release, yesterday it was the release itself, and today it is a whole
  release behind. All three are ordinary. The two implementations tag
  on their own schedules and the interpreter follows the compiler, so the gap
  opens at every compiler release and closes when the mirror catches up.
  A program that answers differently here from a __WOLF_VERSION__ you download
  today may be a disagreement about the text or may only be a difference of
  vintage, and the table below is which. The specification
  is what gets read when it is the first. Counting by ancestry is what makes
  this sayable at a pin that names no tag: the CI job that measures this page
  asks the compiler's history which release the revision descends from and how
  far the tag is, so neither end has to be a tag, and it requires both pages to
  spell what it counted.


  
Where the vintage shows: in no program you can run. Every
  phase: run program in the pinned corpus goes through the module
  this page serves, and at these pins every one of them answers what the
  compiler says it should. There is no table here, because there are no rows to
  put in one.


  
What emptied it was the range arm arriving on this side. At the pin before
  this one match had gained range arms in the compiler and this
  interpreter had been built before that text existed, so it stopped at the
  .. inside a pattern and said E0201 — the refusal
  working as designed, rather than running the program and answering it
  wrongly. The interpreter has the pattern form now, and all four of the
  witnesses that ruling brought in agree with the compiler: the two that run
  (grammar/match_range.lu and
  grammar/match_range_char.lu) exit 0 here, an empty range is
  E0815 here as there, and an open end is still the slice spelling
  and still E0201. That closes wolf-interp#83.


  
The two partings this page named last week are closed.
  They were corpus negatives, refused on both sides and parting in
  which refusal, which is why no table could hold them:
  rows/negative/row_operand_compare.lu puts a bare row beside a
  comparison and answered E0401 here against the compiler's E0409, and
  typecheck/str_slice_assign.lu writes through a slice of a
  str, which was a tier refusal here against the compiler's E0416.
  This interpreter answers E0409 and E0416. That
  closes wolf-interp#85, and it is the reason the pin moved at all.


  
The parting that pointed the other way is closed too, in one
  release. At the last pin this page said something it had never had
  to say: the interpreter took a one-line if —
  if c then a else b — that the compiler refused, because the
  spelling landed on the compiler's trunk after its release was tagged. The
  compiler this page now advertises has it. All nine of the witnesses that
  ruling brought in run here and exit 0, and the three that are refusals are
  refused on both sides. A parting recorded while it was open, and closed by
  the side that was behind, is the whole argument for writing them down.


  
It is a gate now and not only a paragraph. The counted distance above
  compares the texts the two machines were built to read, which is why it was
  blind to this: at the pin before this one it counted no distance at all,
  while the tab ran something your compiler refused. So the build takes that
  program, and every other spelling the interpreter may mirror early, through
  the module it is about to publish, and refuses to ship if one of them runs
  here against a clause the advertised release does not declare.


  
And the parting is back in its usual direction, on the program a
  reader is most likely to try. The compiler's new release rules how a
  Map answers and how an operator reaches a trait, and this
  interpreter was built before either text existed. So
  corpus/memory/map_count.lu — counting words with a
  Map and nothing else, which is exactly what chapter 5 of the
  book teaches — does not run in this tab. Nor does
  corpus/memory/map_int_keys.lu, nor
  corpus/traits/op_money.lu and
  corpus/traits/op_ord_struct.lu, where + and
  < reach an impl the interpreter cannot see yet;
  corpus/traits/op_total_num.lu is refused outright at
  E0201. Three of the five new Map witnesses do run
  — an absent key answering through else, and both key-protocol
  witnesses — so this is a partial mirror and not a blank one, which is the
  useful thing to know and the thing a verdict count alone would hide.


  
Read those four refusals carefully, because they wear a misleading word.
  They report unsupported, the same verdict the tab gives
  net_listen, and they are not the same kind of thing at all. A
  tier refusal is permanent and by design: a page has no sockets. These say
  `+` is not defined on Money and Money, which is this
  interpreter being honestly behind a clause it has not mirrored yet. The
  first will never change here. The second changes at the interpreter's next
  release.


  
What the distance does not explain is what this page declines.
  net_writev and net_nodelay are in this interpreter
  and fs_fstat is declined by design in every build of it, so all
  three report unsupported here whatever the pins say: a tab has
  no sockets, and this interpreter opens no files anywhere. Those refusals are
  the tier and nothing else, and the gap closing has not moved them.


  
The interpreter is not the compiler, and it reaches a different set of
  programs. It runs the memory model as a dynamic machine, so every ownership
  rule is a check at run time and every fault cites the clause it came from. It
  has no type checker and no borrow checker, because those are the compiler's
  half of the split, so a program that the compiler would reject at
  typecheck can still run here. When a program is outside what
  this implementation covers, the verdict is unsupported and the
  reason says which tier declined.


  
What this build declines

  
Seven tiers report unsupported here that work when you run
  lupin at a terminal. Tasks and procs each need an operating
  system thread, and a WebAssembly module in a page has none to spawn. The
  time builtins need a clock the module cannot read, the process
  trio needs processes the page cannot spawn, the net tier needs sockets the
  page cannot open, os_random needs an entropy source the module
  has no way to ask for, and os_signal_listen needs signals
  nothing in a tab can send. The filesystem tier is declined in every build of
  the interpreter, including the terminal one, because it opens no files by
  design. A program whose module graph names sibling files is likewise
  unsupported: the editor is one buffer, and there is no
  directory beside it.

  
os_cpus() is the near miss, and it is worth a sentence
  because the census caught it. This build answers the call now rather than
  declining it — but what it answers is the io row, because a
  wasm module has no way to ask how many cores a process may be scheduled on,
  and [os.cpus] says a host that cannot answer takes that row
  instead of quietly saying one. So corpus/os/cpus.lu stopped
  reporting unsupported when the interpreter grew the call, and
  exits 0 with answered false on the line at every pin since,
  which is the program working as written. It is not on the menu, because its own header says
  answered true and a sample shown beside a header it contradicts
  looks broken.


  
__COUNT_netprograms_Word__ of the corpus's net programs land in that
  count, and none of them moved at this release. The three newest are v0.2.8's
  — syscall_first.lu, writev_gather.lu and
  nodelay.lu, the witnesses for a read that no longer takes a
  round trip through the reactor, for a head and a body leaving as one write,
  and for Nagle being off on every stream the runtime hands out. A tab declines
  all three for one reason only, which is the socket: the calls themselves have
  been in this interpreter since 0.1.28, and while they were not, a sentence
  here said the refusal had two causes. That count was wrong until ww19,
  incidentally. The page said twelve from ww16, when thirteen was already the
  number; nothing gates a count written by hand, and re-measuring the census is
  what caught it.


  
Every sample on the menu runs

  
All __COUNT_samples_word__ of them, and none carries a note. The newest is
  match on a range — corpus/grammar/match_range.lu,
  which was kept off the menu at exactly one pin and for exactly one reason: it
  answered E0201 in this tab, and an entry that answers
  fail looks broken whatever the page says beside it. The reason
  expired when the interpreter gained the pattern form, so the program a
  reader could not run here a week ago is the one the menu now opens with.
  Press Run and the tab agrees with the compiler byte for byte. Beside it is
  match as a switch —
  corpus/grammar/match_switch.lu, which was on the menu through
  that whole pin, because its guarded arm is a lowering the compiler gained and
  not a pattern form, so this interpreter had always run it. The two sat one
  ruling apart and on opposite sides of the menu, and the distance between them
  was the whole of what the vintage cost. The one before them was text
  to a number, and the row when it is not —
  corpus/strings/to_int.lu, the call the book's chapter 1 makes
  in its cold open. It reached the menu when the compiler gained the call
  rather than when the interpreter did, and the reason runs against the usual
  direction: the interpreter has answered str.to_int all along, so
  the program the tab could always have run is the one that only just started
  compiling. That was not true
  at
  the lupin 0.1.24 pin: the menu's byte, and its cast ladder —
  corpus/typecheck/byte_casts.lu — answered
  fail(E0301) here and carried a note on this page saying so,
  because byte was the compiler's headline at v0.2.4 and the
  interpreter beside it had been built against the release before. lupin
  0.1.25 closed that and it has stayed closed. Press Run on it and it prints
  the line its own header claims:


widen 200 200 | trunc 0 255 0 255 44 | arith 201 400 -1 -200 | order true true true | eq true true

  
which is the whole ruling in one line: 200 as byte widens
  back to 200 and never -56, 256 truncates to 0 and -1
  to 255 and 300 to 44 without a trap or a warning, arithmetic
  widens to int before it computes so 200 + 200 is
  400, and the comparisons are octet order.

  
Nothing on this page decided that by hand. A gate in this site's CI feeds
  every program in the menu to the module the build publishes and requires each
  one to answer in the class the page claims for it — so a sample that stops
  running goes red, and so does a note that outlives the refusal it explains.
  That is how the note above came off: the gate went red at this pin, naming
  the sample, and the sentence had to go.


  
The verdict vocabulary

  

    
verdictwhat happened

    
exit(N)The program ran to completion and returned N.

    
trap(kind)A checked fault stopped it: overflow, a bad index, a use after move. Each kind is a closed vocabulary entry and cites a clause.

    
fail(CODE)The program was rejected before it ran, with that diagnostic code.

    
ub(anchor)The provenance oracle found undefined behavior, and names the row of the memory model that licenses it.

    
unsupportedOutside this implementation's coverage. The reason names the tier.
