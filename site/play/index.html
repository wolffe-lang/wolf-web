Warnings

      

      
The interpreter runs a subset of the compiler's warning
        analyses, so a program the compiler warns about can come back clean
        here. lupin reports these in its observation record, and at
        a terminal they stay there.

    


    

      
Observation record

      

      
The line lupin run - --json prints: the
        spec/06 observation record, which is the only thing the compiler and the
        interpreter compare through. A program that traps now carries what it
        printed before it died in stdout_inline. Through
        v0.1.22 that field was null on every trapping program, so
        the two implementations were record-identical whatever they printed —
        and one real disagreement about what a trap does to a pending
        defer sat behind it, unmeasured, until v0.1.23.

    

  






  
What is running

  
lupin is the wolf reference interpreter. It is a separate
  implementation from the compiler, written against the specification, and the
  two share no code. The build in this page is that program, compiled to
  WebAssembly from the revision this site was built from. Nothing is uploaded:
  the source stays in the tab, and no request leaves the page after the module
  and the samples have loaded.


  
The revision of the specification it reads is not the compiler's. This
  interpreter, lupin __LUPIN_VERSION__, was released against the wolf release
  before __WOLF_VERSION__ — the one install
  advertises — so it is one release behind on the spec, and a program can
  answer here differently from a wolf you download today for no reason worse
  than that. Where the two disagree, the specification is
  what gets read.


  
The interpreter is not the compiler, and it reaches a different set of
  programs. It runs the memory model as a dynamic machine, so every ownership
  rule is a check at run time and every fault cites the clause it came from. It
  has no type checker and no borrow checker, because those are the compiler's
  half of the split, so a program that the compiler would reject at
  typecheck can still run here. When a program is outside what
  this implementation covers, the verdict is unsupported and the
  reason says which tier declined.


  
What this build declines

  
Five tiers report unsupported here that work when you run
  lupin at a terminal. Tasks and procs each need an operating
  system thread, and a WebAssembly module in a page has none to spawn. The
  time builtins need a clock the module cannot read, the process
  trio needs processes the page cannot spawn, and the net tier needs sockets
  the page cannot open. The filesystem tier is declined in every build of the
  interpreter, including the terminal one, because it opens no files by
  design. A program whose module graph names sibling files is likewise
  unsupported: the editor is one buffer, and there is no
  directory beside it.


  
One sample this build refuses

  
The menu's byte, and its cast ladder is
  corpus/typecheck/byte_casts.lu, and pressing Run on it gets
  fail(E0301) rather than a program. That is the pin gap above,
  with a face on it. byte — an 8-bit unsigned octet — is the
  compiler's headline at v__WOLF_VERSION__, and it landed after the wolf
  release lupin __LUPIN_VERSION__ was built against, so as byte
  names no type this interpreter resolves and it says so at the cast. The
  program is on the menu anyway because reading it is the point: the header
  states what the cast ladder is supposed to print, the compiler prints that,
  and this machine does not have the type yet. It is one of nine corpus
  programs dark here for that reason, and there is a tenth for another —
  grammar/bom_at_start.lu,
  whose leading byte order mark this interpreter refuses and the compiler
  strips.

  
Nothing on this page decides that by hand. A gate in this site's CI feeds
  every program in the menu to the module the build publishes and requires each
  one to answer in the class the page claims for it — so a sample that stops
  running goes red, and the note above goes red the day the interpreter starts
  running it.


  
The verdict vocabulary

  

    
verdictwhat happened

    
exit(N)The program ran to completion and returned N.

    
trap(kind)A checked fault stopped it: overflow, a bad index, a use after move. Each kind is a closed vocabulary entry and cites a clause.

    
fail(CODE)The program was rejected before it ran, with that diagnostic code.

    
ub(anchor)The provenance oracle found undefined behavior, and names the row of the memory model that licenses it.

    
unsupportedOutside this implementation's coverage. The reason names the tier.
