install

What the published archives do on each platform, measured rather than assumed.

wolf install playground the book docs spec changelog

Every tagged release uploads an archive per host to the releases page. An archive is a folder with the wolf binary in it and the runtime archive it links programs against — there is no installer and nothing to register. On macOS and linux a package manager will do it for you instead: the doors are below. Building from source is the path the project itself uses; the recipe is on the front page.

Wolf is version __WOLF_VERSION__ and pre-alpha. This page describes that release and no other.

Package managers

Two channels carry wolf, and the project publishes both. On macOS and linux, a Homebrew tap — three lines, and the first one is not optional:

brew trust wolffe-lang/wolf
brew tap wolffe-lang/wolf
brew install wolf

Skip brew trust and Homebrew tells you something that is not true. It declines to load formulae from a third-party tap you have not trusted, and then reports the refusal in its generic words:

Refusing to load formula wolffe-lang/wolf/wolf from untrusted tap wolffe-lang/wolf.
Error: Cannot tap wolffe-lang/wolf: invalid syntax in tap!

There is no syntax error. Both formulae parse, and the second line is what Homebrew says about any tap it declined to read, whatever the reason. Trust the tap and it taps cleanly. The tap carries three formulae: wolf, the compiler; lupin, the reference interpreter; and lobo, the web server this project is writing in wolf. The first two build from the tagged git source rather than a release archive, which is deliberate — a build made at the tag is what lets wolf --version print a bare version and a pin instead of the +dev suffix an unverifiable build carries, and each formula's test block asserts that before the binary reaches you.

Arch

On the AUR the packages are named for the language rather than for the compiler, because wolf was taken a long time ago: it is Return to Castle Wolfenstein, and installing it gets you a first-person shooter that wants the retail game files. What you want is

yay -S wolf-lang-bin

and there are five packages in all. wolf-lang and wolf-lang-bin are the compiler, built at the tag and unpacked from the published archive respectively; lupin and lupin-bin are the interpreter the same two ways; and lobo-bin is the server. The -bin packages are the fast door, and they install the same archives the releases page serves.

Neither channel is built by this site, and nothing on this page can tell you they are current. What can is a gate in the tap's own repository that reads what is published — the live AUR, the live tap, the live release pages — and goes red when a package trails its upstream or names a digest the release does not carry. When this page was last read against the pins, every channel agreed — and the page it replaces, written a few hours earlier, had to report that they did not. That is worth a sentence, because it is what the gate is for. At the previous pin the tap had already moved past this page while the AUR had not moved at all: one door ahead, one behind, neither wrong. Both have since landed here. The tap's wolf formula builds tag v__WOLF_VERSION__ and its lupin builds __LUPIN_VERSION__; on the AUR both compiler packages read __WOLF_VERSION__ and both interpreter packages __LUPIN_VERSION__. Do not expect the tidy reading every time: a release and its packaging are separate acts and do not land in the same minute, which is the distance that gate exists to watch. The archives below are the release itself, and need nothing installed first.

Windows

The compiler builds and runs native Windows programs, and the concurrency and operating-system surface is among what it runs. wolf build hello.lu writes hello.exe and wolf run hello.lu compiles and executes it — machine code on the host, not an interpreter. Native compilation arrived at v0.2.2 refusing a whole region by name — tasks, channels, os.signal, twenty-one programs of the conformance corpus that this page listed one by one — and v0.2.3 took that paragraph off the page. Three of those programs run on a Windows box every time this site changes, which is how the sentence stays a measurement.

There is one thing to install first, and it is not wolf's: Visual Studio Build Tools with the "Desktop development with C++" workload. Linking any Windows program needs import libraries — kernel32.lib, the UCRT, msvcrt.lib — that ship with the Windows SDK and the MSVC toolset rather than with Windows itself. It is the same requirement Rust's own windows-msvc toolchain carries. Without it wolf refuses before it links, and the refusal is quoted in full below.

Nothing here is guessed. A job in this site's own CI downloads the archive linked below onto a Windows runner, unpacks it with the same command you are about to type, and asserts every claim on this page — the successes and the refusals alike, word for word and exit code for exit code. It runs on every change to this site and once a week besides, so a sentence here that stops being true goes red before you find out the hard way. The no-toolchain refusal is measured too: the job takes the Windows SDK away from its own runner for the length of one command, so the sentence below is a transcript rather than a paraphrase.

Get it

Download wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc.tar.gz — about 11 MB — then unpack it in PowerShell. tar has shipped with Windows since Windows 10 build 1803, so nothing needs installing to open this:

tar -xzf wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc.tar.gz

That leaves a folder holding wolf.exe, the C-import worker, the runtime library wolf_rt.lib and the licenses. Keep them together: wolf.exe cannot link a program without wolf_rt.lib beside it. Move the folder wherever you keep tools and put it on your PATH. For one PowerShell session:

$env:Path = "C:\tools\wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc;$env:Path"

To keep it, add the same folder to your user PATH under Settings → System → About → Advanced system settings → Environment Variables. Then, in a new window:

wolf --version
wolf __WOLF_VERSION__ (wolfgang, pin …)
paired with lupin __LUPIN_VERSION__ (reference interpreter), pin …

Two lines: the release and the commit it was built at, then the lupin release it was differentially tested against and the specification pin that release was built to. A binary never claims a release it is not — anything but a build made at the tag says so in that first line.

Read the second line closely, because it is the one that moves, and at these pins it has moved again. lupin __LUPIN_VERSION__ names __PIN_specrev_short__ as the specification it was built to. That is a release tag rather than a revision of the compiler's trunk — but it is the tag before this one, __COUNT_speccommits_word__ commits back, so the newest release whose text the interpreter carries whole is one release behind the compiler you are installing. This is the resting state, and the page said so yesterday when the gap was closed: a gap opens whenever the compiler tags and the interpreter has not yet followed, which is the ordinary shape of a two-implementation project. While it is open the playground can answer a program differently from the compiler you just installed. When the two disagree, the specification is what gets read.

What the gap costs, concretely, is a short list of corpus programs. The two messages that parted two pins ago are settled — a bare row used as an operand is E0409 in both places now, and a write through a str slice is E0416 in both (wolf-interp#85, closed) — and the range arms that parted the pin before that have been on both sides since: corpus/grammar/match_range.lu and corpus/grammar/match_range_char.lu run in the tab and with the compiler above and agree, as do the empty range and the open end the same ruling brought in (wolf-interp#83, closed). Both witnesses stay named here after their parting closed, because a page that records a disagreement only while it is open leaves a reader no way to check that it ever ended.

At the last pin this page described a parting running the other way — the interpreter took a one-line if, if c then a else b, that the compiler refused. This release is the compiler taking it. Every running witness of that ruling now agrees in both places, so the reversed parting lasted exactly one release and is recorded here because it happened, not because it lasted.

What the new gap costs is in the other direction again, and it lands somewhere a reader will actually stand. This release rules how a Map answers and how an operator reaches a trait, and the interpreter was built before either text existed. So counting words with a Map alone — corpus/memory/map_count.lu, the program chapter 5 of the book is now built around — runs under the compiler above and does not run in the tab. Four others go with it: map_int_keys.lu, traits/op_money.lu and traits/op_ord_struct.lu, where + and < cannot reach their impl yet, and traits/op_total_num.lu, refused outright. Most of the new Map witnesses do run there, so the mirror is partial rather than absent; the playground counts them exactly. Nothing else in the corpus this release ships answers differently in the two places, and no program that ran in the tab before this release stopped.

A gap of any width does not make the playground run everything, either, and it never did. net_writev and net_nodelay are in this interpreter and fs_fstat is declined by design in every build of it, so all three are refused in the tab whatever the pins say: a browser has no sockets, and the interpreter opens no files anywhere. The CI job that measures this page counts the gap against the compiler's own changelog — by ancestry, because the interpreter's pin need not be a tag — and requires this page and the playground's to spell what it counted, so the sentence goes red when it stops being true rather than quietly rotting.

Your first program

Make a folder and put one file in it. The folder matters: every .lu file in a directory is one module, so two files each with a main is a duplicate definition (E0302) rather than two programs. hello.lu:

fn main() -> !int {
    let who = "wolf"
    print("hello, {who}")
    0
}

From that folder:

wolf run hello.lu
hello, wolf

Exit code 0. wolf build hello.lu stops one step earlier and leaves hello.exe beside the source, which you can run, move, or send to someone who has no wolf installed at all — it is an ordinary Windows executable. wolf run --checked hello.lu builds the same program against the checked runtime, which watches for the undefined behaviour an ordinary build is allowed to assume away, and runs that instead; it prints the same hello, wolf.

If you are curious which linker it used, wolf build --verbose says so on the last line — on the runner that measures this page it reads wolf build: windows linker: lld-link (lld-link on PATH). Wolf looks for WOLF_LINKER, then lld-link, then the rust-lld a Rust toolchain already carries, then MSVC link.exe, and takes the first one it finds.

The byte, the moment you touch a string's octets

Wolf has a byte-width scalar — byte, an 8-bit unsigned octet, 0..=255 — and every builtin that produces or takes raw octets speaks List[byte] where it used to say List[int]. It arrived at v0.2.4 as a breaking change, and it stays on an install page rather than sinking into a changelog because it is the first hour of wolf, not the release notes: the first thing anyone does with a byte is compare it to a number, and a byte adopts no numeric literal. So this does not build:

let b = s.bytes()[0]
if b == 119 { print("w") }

The compiler finishes the sentence rather than leaving you to guess which side to change:

error[E0401]: this is `{integer}`, but the other side of `==` makes it `byte`
  = note: `byte` adopts no literal and takes no `int` implicitly ([type.byte]):
    widen the byte — `b as int` — or narrow this side with `as byte`, which
    keeps the value's low eight bits ([type.byte.cast]).

Exit code 1 — an ordinary program that does not compile, which is a different thing from the exit 2 this host's own refusals answer with. One line per site, and the note names the line. Comparisons and arithmetic against integers want as int, which widens by zero-extension; a value going back into a byte list wants as byte, which keeps the low eight bits and never traps. The same refusal, with the same note, meets an index (table[b]), a binding written let n: int = b, and a literal match arm. Nothing widens behind your back, which is the point of a scalar that carries its width. The job that measures this page builds the broken program above on a Windows runner and reads that note back, then builds the fixed one and runs it.

What you see without Build Tools

You do not need a Developer Command Prompt: wolf finds the Visual Studio installation itself, and the CI job asserts that from an ordinary shell with LIB unset and PATH cut back to Windows plus the wolf folder. What you do need is for the toolset to be installed at all. On a machine where it is not, wolf build hello.lu answers:

wolf build: windows-native: no MSVC toolset / Windows SDK found — the
import libraries every linker needs (kernel32.lib, the UCRT, msvcrt.lib)
come with Visual Studio Build Tools' "Desktop development with C++"
workload (MSVC x64 + Windows SDK); install that, or run from a Developer
Command Prompt (LIB set). Bundling the libraries so no install is needed
is s47's (the s60 campaign).

Exit code 2, wrapped here and printed on one line there; wolf run says the same thing in the same words. It is a refusal before the link rather than a link error afterwards, which is the difference between a message that tells you what to install and a wall of unresolved symbols. Installing the workload is the whole fix. Shipping the import libraries inside the archive so that nothing has to be installed is planned work, and the refusal names it.

What still refuses

Five things a program can reach, and every one of them is named to your face rather than quietly becoming something else. One is the compiler's own refusal, exit 2. One is a gap in what the Windows console gives a program. Three are the unsupported row — a value your program can read and branch on, which is the difference between code that can serve this host differently and code that cannot. Two of those three arrived at v0.2.5, the release that made a prefork server writable, because this is the host where a prefork server is written a different way. (The ledger at the end of this section has the rest, none of which a first program meets.)

wolf build --release, the LLVM optimizing tier, refuses this host with exit code 2:

wolf build: this host cannot run the release tier: the release
tier targets linux/x86-64 and macOS/aarch64 (s41 + s127; c13 owns the
matrix) — this host is neither, and further platforms follow as their
own sprints

Wrapped here and printed on one line there. The plain wolf build is the one you want on Windows today, and it is a real native build: the same machine code through the compiler's own backend, without an LLVM pass pipeline over it.

External reload and upgrade signals have nothing on Windows to arrive through. The console offers Ctrl+C, Ctrl+Break and the window closing — which wolf reads as terminate and quit — and nothing at all that means "reload". Inside your own program every meaning works: the corpus's signal witness listens for reload, raises it, waits for it and prints reload, and the CI job runs that program on a Windows runner and reads exactly that back. What you cannot do is send one from another process, so a long-running program that wants reload or upgrade on this host takes them over a control channel instead.

Unix-domain sockets — net_listen_unix and net_connect_unix, new at v0.2.4 — answer the unsupported row on this host. By name, rather than as a bare io failure: the difference is whether a program can branch on the host at all, and it is the whole reason the row exists. AF_UNIX has been in Windows since build 1803 and the compiler's own test suite measures the kernel's answer on a runner, but the runtime carries no winsock binding for the family, so the ledger names the rung instead of claiming it. A program that wants a local control endpoint here keeps it on loopback TCP. The job that measures this page runs the corpus's unix witness on a Windows box and reads the named row back from it.

A shared listening address — net_listen_with's reuse_port option — answers the unsupported row here, and this one is a refusal on purpose rather than a binding nobody has written yet. Windows has no SO_REUSEPORT. It has SO_REUSEADDR, which is spelled like a synonym in a manual and means something else entirely: it lets any process take a port another process already holds, and promises nothing about which of them a connection reaches. The compiler's own Windows suite measured what the alias would have bought — two sockets both carrying it bound one port, and every one of sixteen dials went to the first socket bound, none to the second — so a worker that thought it had joined a group would sit idle forever with nothing to report. Refusing by name is the better answer, and it is the one you get. net_listen_with without the option serves this host exactly like net_listen, backlog hint included, and an address already held answers exists by name rather than a bare io.

Handing a descriptor to a child — os_spawn_with's inherit set, and the net_adopt_listener on the other side of it — answers the unsupported row too. Two things are missing rather than one, and both were measured rather than assumed: a listener's SOCKET marked inheritable and named to a re-executed child is not a usable socket in that child at all, because the spawn the runtime performs publishes only stdio handles to it; and a SOCKET is not the small stable number the clause hands over by position, so "the listener is 3" has nothing to be true of. os_spawn_with with an empty set already works — it is os_spawn with the program named apart from its arguments — so what a Windows port of a prefork master waits on is the handoff, not the spawn.

What that leaves is the call v0.2.5 was named for, and it is here. net_wait — readiness over a whole set of handles, the thing a serving loop has instead of a scheduler — is the one socket clause s137 added that names no refusal on any host: poll(2) and WSAPoll answer the same question, and the corpus's witness for it runs on this host in the job that measures this page. os_cpus() answers here too. So a single-process server that waits on many sockets is written the same way on Windows as anywhere; it is the many-processes-one-port shape that takes a different route.

The fair accept v0.2.6 was named for is here too, and it is not a new call — it is what net_accept already did, corrected. Windows is one of the three reactor hosts the clause names, so a listener lives non-blocking under the runtime here as well: a hand woken by an arrival that another hand took waits again against the budget its net_deadline armed, rather than in the kernel's accept queue. Nothing a program written against v0.2.5 does changes. What the correction would buy this host is the prefork shape, and that still waits on the descriptor handoff above — a single-process Windows server accepting on its own listener never loses the race in the first place.

Everything else the language has is here. Tasks and scopes, proc, channels and select, sync/ when, region transfer, os.signal and network deadlines all compile and run, alongside everything a first month of wolf touches — printing, strings, lists, JSON, files, environment and child processes, time, random, regions and the region ledger, and TCP sockets. The release records this host at macOS parity across the conformance corpus, with no row refused by construct name at all: the thirty-six rows the native lane does not execute here are exactly the thirty-six it does not execute on macOS, which makes them the lanes' own scope gaps rather than this host's. A stack overflow inside a task reports in wolf's own words — wolf-rt: stack overflow in task '…', exit 134 — while one in a program that never spawns still dies as a bare 0xC00000FD, because the reporter is installed when the task pool starts and a program with no tasks never starts one.

The compiler's own per-host ledger is docs/platforms.md at the release tag: the table of what each host serves, the refusals row by row, the linker order in full, and the named sprints that close the gaps — including two this page does not measure because no first program meets them, structs passed by value across the extern "c" boundary and the debugger.

Line endings

If you wrote hello.lu in Notepad, it has Windows line endings, and:

wolf fmt --check .\hello.lu
wolf fmt --check: ./hello.lu is not canonically formatted

Exit code 1. Canonical wolf source is LF, and wolf fmt hello.lu rewrites the file — line endings included — after which the check passes. The formatter has no options, so there is nothing to configure and nothing to argue about.

Two more verbs

wolf test hello.lu runs the program and reports a verdict instead of its output — test hello.lu::main ... ok, then 1 passed; 0 failed. It is the short way to ask whether a program still works.

wolf conform-run hello.lu --checked is also available, and it is a different thing: a conformance harness rather than a runner. It executes your program on the compiler's own checked machine — no code generation, no linker, so it works on a box with no Build Tools at all — and prints a one-line machine record instead of your output:

{"commit":"…","diagnostics":[],"file":"./hello.lu","impl":"wolfgang",
 "impl_version":"__WOLF_VERSION__","phase_reached":"run","protocol":1,
 "seeded":false,"stdout_inline":"hello, wolf\n","stdout_sha256":"…",
 "verdict":"exit(0)","warnings":[]}

Wrapped here; the build commit and the output digest are elided. Your program's output is the stdout_inline field. Drop --checked and it stops before code generation and answers "verdict":"unsupported". Through v0.2.1 this was the only way to run a program on Windows, and this page led with it; it is now the specialist's tool it was always meant to be.

The interpreter, and the playground

Wolf has a second implementation: lupin, a reference interpreter written against the same specification, sharing no code with the compiler. It is now published for Windows as a single file — lupin.exe, about 5 MB, no installer and nothing beside it. Running a file takes no subcommand:

lupin hello.lu
hello, wolf

It is a good second opinion when the compiler and your expectations disagree — a different implementation reading the same specification, not a fallback for what the backend cannot do. That distinction had to be won: through v0.2.2 lupin was also the only way to run a program on this host that used a task or a channel, and it has not been that since v0.2.3. lupin --version names the release and the specification pin it was built against, which is the pin the second line of wolf --version quotes back — __PIN_specrev_short__ at these pins, which is the tag before this compiler's, as measured above.

The playground runs that same interpreter compiled to WebAssembly — lupin __LUPIN_VERSION__, in the tab, with the corpus programs to load, and nothing to download at all. Its editor is exercised on a Windows runner in this site's CI, in the Ctrl spelling a Windows browser sends rather than the Cmd one; the single Windows-specific catch is a hotkey some graphics drivers take before the browser sees it, and the playground page names it beside its key bindings.

Everywhere else

linux x86-64 and macOS aarch64 are the two hosts the whole toolchain is built and tested on: wolf run compiles to native machine code through the compiler's own backend and executes it, wolf build --release goes through LLVM, and the concurrency runtime is all there. Take the archive for your platform from the releases page and put its folder on your PATH — the binary and the runtime archive have to stay together, because the binary cannot link a program without it.

__WOLF_VERSION__ carries four archives, one for every tier-1 host: those two, windows x86-64, and linux aarch64. That last one has no native backend behind it yet, so what its archive serves is the checked tier — wolf test and wolf conform-run --checked run your program, wolf run refuses the host by name — and v0.2.2 shipped no arm archive at all, because the smoke that gates the upload could not tell an unserved host from a broken build. Every release since carries it. All four URLs are asked for a 200 by the same job that measures the Windows section, every time this site changes. For a host outside the matrix, the source recipe is the path.

The front page has the four lines that build the same toolchain from source, which is the path the project itself is known to work on.

The Windows facts on this page were measured on a Windows runner against the published archive, by a job that reruns weekly. If the page and the archive disagree, the archive is right and the job is about to say so.
