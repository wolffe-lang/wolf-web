What the published archives do on each platform, measured rather than assumed.

Every tagged release uploads archives to the releases page: linux x86-64 and aarch64, macOS aarch64, and Windows x86-64. An archive is a folder with the wolf binary in it and the runtime archive it links programs against — there is no installer and nothing to register. Building from source is the path the project itself uses; the recipe is on the front page.

Wolf is version __WOLF_VERSION__ and pre-alpha. This page describes that release and no other.

Windows

Read this part before you download anything, because it decides whether the rest is worth your evening: the compiler cannot yet produce a Windows executable. wolf build and wolf run refuse this host by name. Everything in front of code generation works — the parser, the type and region checkers, the formatter, the diagnostics — and a checked machine inside the compiler will execute your program and show you its output. That is a real first day with the language, and it is less than a Linux or macOS learner gets. Both halves are below.

Nothing here is guessed. A job in this site's own CI downloads the archive linked below onto a Windows runner, unpacks it with the same command you are about to type, and asserts every claim on this page — the refusals included, word for word and exit code for exit code. It runs on every change to this site and once a week besides, so a sentence here that stops being true goes red before you find out the hard way.

Get it

Download wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc.tar.gz, then unpack it in PowerShell. tar has shipped with Windows since Windows 10 build 1803, so nothing needs installing to open this:

tar -xzf wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc.tar.gz

That leaves a folder holding wolf.exe, the C-import worker, the runtime library wolf_rt.lib and the licenses. Move the folder wherever you keep tools and put it on your PATH. For one PowerShell session:

$env:Path = "C:\tools\wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc;$env:Path"

To keep it, add the same folder to your user PATH under Settings → System → About → Advanced system settings → Environment Variables. Then, in a new window:

wolf --version

It answers with wolf __WOLF_VERSION__, the commit it was built at, and the lupin release it was differentially tested against. A binary never claims a release it is not: anything but a build made at the tag says so in that line.

Your first program

Make a folder and put one file in it. The folder matters: every .lu file in a directory is one module, so two files each with a main is a duplicate definition rather than two programs. hello.lu:

fn main() -> !int {
    let who = "wolf"
    print("hello, {who}")
    0
}

From that folder, run it:

wolf conform-run .\hello.lu --checked
{"commit":"…","diagnostics":[],"file":"./hello.lu","impl":"wolfgang",
 "impl_version":"__WOLF_VERSION__","phase_reached":"run","protocol":1,
 "seeded":false,"stdout_inline":"hello, wolf\n","stdout_sha256":"…",
 "verdict":"exit(0)","warnings":[]}

That is one line in the record; it is wrapped here, and the build commit and the output digest are elided. Your program's output is the stdout_inline field — hello, wolf — and verdict is the exit status it returned. This is a conformance harness rather than a nice runner, and on Windows today it is the way a program runs.

Two things about that command line are load-bearing. --checked is what makes it run: it hands your program to the compiler's checked machine, which executes it directly and watches for the undefined behaviour a native build would let past. Drop the flag and the same command stops before code generation and answers "verdict":"unsupported". And write .\hello.lu, not hello.lu: a bare filename makes this one command answer the package root has no wolf source files, which is wolf-lang#206 and describes nothing you did wrong.

wolf test .\hello.lu runs on the same machine and reports 1 passed instead of your output, which is the shorter way to ask whether a program still works.

What refuses, and what that means

wolf build .\hello.lu
wolf build: this host cannot run the native tier: native codegen targets
linux/x86-64 and macOS/aarch64 (s28 + s59; the rest of D35's matrix is
c13) — host: x86_64-pc-windows-msvc

Exit code 2, and wolf run says the same thing in the same words. It is an honest refusal rather than a crash: native code generation serves linux/x86-64 and macOS/aarch64 today, this host is neither, and the compiler declines instead of half-working. wolf run --checked refuses identically — on the native path that flag selects a checked build, which still needs the code generator this host does not have, and it is not the --checked of the paragraph above. Native Windows builds are in progress. This page will not name a date; it will change when the job that measures it measures something else.

Line endings

If you wrote hello.lu in Notepad, it has Windows line endings, and:

wolf fmt --check .\hello.lu
wolf fmt --check: ./hello.lu is not canonically formatted

Exit code 1. Canonical wolf source is LF, and wolf fmt .\hello.lu rewrites the file — line endings included — after which the check passes. The formatter has no options, so there is nothing to configure and nothing to argue about.

The interpreter, and the playground

Wolf has a second implementation: lupin, a reference interpreter written against the same specification, sharing no code with the compiler. It would be the natural thing to hand a Windows learner, and it is not published as a binary — for Windows or for anything else (wolf-interp#54). This page will not point you at a Linux tarball and wish you luck.

What you can have today is the same interpreter compiled to WebAssembly: the playground runs lupin __LUPIN_VERSION__ in the tab, with the corpus programs to load, and it behaves on Windows exactly as it does anywhere else. If you want to watch a program run while the native tier is still on its way, that is the place.

Everywhere else

On linux x86-64 and macOS aarch64 the whole toolchain works: wolf run compiles to native machine code through the compiler's own backend and executes it, and wolf build --release goes through LLVM. Take the archive for your platform from the releases page and put its folder on your PATH — the binary and the runtime archive have to stay together, because the binary cannot link a program without it. linux aarch64 gets archives at every tag without a CI runner behind them yet.

The front page has the four lines that build the same toolchain from source, which is the path the project itself is known to work on.

The Windows facts on this page were measured on a Windows runner against the published archive, by a job that reruns weekly. If the page and the archive disagree, the archive is right and the job is about to say so.
