install

What the published archives do on each platform, measured rather than assumed.

wolf install playground the book docs spec changelog

Every tagged release uploads an archive per host to the releases page. An archive is a folder with the wolf binary in it and the runtime archive it links programs against — there is no installer and nothing to register. Building from source is the path the project itself uses; the recipe is on the front page.

Wolf is version __WOLF_VERSION__ and pre-alpha. This page describes that release and no other.

Windows

The compiler builds and runs native Windows programs, and the concurrency and operating-system surface is among what it runs. wolf build hello.lu writes hello.exe and wolf run hello.lu compiles and executes it — machine code on the host, not an interpreter. Native compilation arrived at v0.2.2 refusing a whole region by name — tasks, channels, os.signal, twenty-one programs of the conformance corpus that this page listed one by one — and v0.2.3 took that paragraph off the page. Three of those programs run on a Windows box every time this site changes, which is how the sentence stays a measurement.

There is one thing to install first, and it is not wolf's: Visual Studio Build Tools with the "Desktop development with C++" workload. Linking any Windows program needs import libraries — kernel32.lib, the UCRT, msvcrt.lib — that ship with the Windows SDK and the MSVC toolset rather than with Windows itself. It is the same requirement Rust's own windows-msvc toolchain carries. Without it wolf refuses before it links, and the refusal is quoted in full below.

Nothing here is guessed. A job in this site's own CI downloads the archive linked below onto a Windows runner, unpacks it with the same command you are about to type, and asserts every claim on this page — the successes and the refusals alike, word for word and exit code for exit code. It runs on every change to this site and once a week besides, so a sentence here that stops being true goes red before you find out the hard way. The no-toolchain refusal is measured too: the job takes the Windows SDK away from its own runner for the length of one command, so the sentence below is a transcript rather than a paraphrase.

Get it

Download wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc.tar.gz — about 11 MB — then unpack it in PowerShell. tar has shipped with Windows since Windows 10 build 1803, so nothing needs installing to open this:

tar -xzf wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc.tar.gz

That leaves a folder holding wolf.exe, the C-import worker, the runtime library wolf_rt.lib and the licenses. Keep them together: wolf.exe cannot link a program without wolf_rt.lib beside it. Move the folder wherever you keep tools and put it on your PATH. For one PowerShell session:

$env:Path = "C:\tools\wolf-__WOLF_VERSION__-x86_64-pc-windows-msvc;$env:Path"

To keep it, add the same folder to your user PATH under Settings → System → About → Advanced system settings → Environment Variables. Then, in a new window:

wolf --version
wolf __WOLF_VERSION__ (wolfgang, pin …)
paired with lupin __LUPIN_VERSION__ (reference interpreter), pin …

Two lines: the release and the commit it was built at, then the lupin release it was differentially tested against and the specification pin that release was built to. A binary never claims a release it is not — anything but a build made at the tag says so in that first line.

Read the second line closely, because it is the one that moves. At these pins the two commits ARE the same commit: lupin __LUPIN_VERSION__ was released against __WOLF_VERSION__ itself, so the reference interpreter and the compiler are reading one revision of the specification and the gap is zero. It is usually one — the ordinary shape of a two-implementation project between tags, and the reason the playground can answer a program differently from the compiler you just installed. When they disagree, the specification is what gets read. The CI job that measures this page checks the gap is zero or one release and prints which, so this sentence goes red when it stops being true rather than quietly rotting.

Your first program

Make a folder and put one file in it. The folder matters: every .lu file in a directory is one module, so two files each with a main is a duplicate definition (E0302) rather than two programs. hello.lu:

fn main() -> !int {
    let who = "wolf"
    print("hello, {who}")
    0
}

From that folder:

wolf run hello.lu
hello, wolf

Exit code 0. wolf build hello.lu stops one step earlier and leaves hello.exe beside the source, which you can run, move, or send to someone who has no wolf installed at all — it is an ordinary Windows executable. wolf run --checked hello.lu builds the same program against the checked runtime, which watches for the undefined behaviour an ordinary build is allowed to assume away, and runs that instead; it prints the same hello, wolf.

If you are curious which linker it used, wolf build --verbose says so on the last line — on the runner that measures this page it reads wolf build: windows linker: lld-link (lld-link on PATH). Wolf looks for WOLF_LINKER, then lld-link, then the rust-lld a Rust toolchain already carries, then MSVC link.exe, and takes the first one it finds.

The byte, the moment you touch a string's octets

At __WOLF_VERSION__ wolf has a byte-width scalar — byte, an 8-bit unsigned octet, 0..=255 — and every builtin that produces or takes raw octets now speaks List[byte] where it used to say List[int]. That is the release's headline, and it is a breaking change, which is why it is on an install page rather than only in a changelog: the first thing anyone does with a byte is compare it to a number, and a byte adopts no numeric literal. So this does not build:

let b = s.bytes()[0]
if b == 119 { print("w") }

The compiler finishes the sentence rather than leaving you to guess which side to change:

error[E0401]: this is `{integer}`, but the other side of `==` makes it `byte`
  = note: `byte` adopts no literal and takes no `int` implicitly ([type.byte]):
    widen the byte — `b as int` — or narrow this side with `as byte`, which
    keeps the value's low eight bits ([type.byte.cast]).

Exit code 1 — an ordinary program that does not compile, which is a different thing from the exit 2 this host's own refusals answer with. One line per site, and the note names the line. Comparisons and arithmetic against integers want as int, which widens by zero-extension; a value going back into a byte list wants as byte, which keeps the low eight bits and never traps. The same refusal, with the same note, meets an index (table[b]), a binding written let n: int = b, and a literal match arm. Nothing widens behind your back, which is the point of a scalar that carries its width. The job that measures this page builds the broken program above on a Windows runner and reads that note back, then builds the fixed one and runs it.

What you see without Build Tools

You do not need a Developer Command Prompt: wolf finds the Visual Studio installation itself, and the CI job asserts that from an ordinary shell with LIB unset and PATH cut back to Windows plus the wolf folder. What you do need is for the toolset to be installed at all. On a machine where it is not, wolf build hello.lu answers:

wolf build: windows-native: no MSVC toolset / Windows SDK found — the
import libraries every linker needs (kernel32.lib, the UCRT, msvcrt.lib)
come with Visual Studio Build Tools' "Desktop development with C++"
workload (MSVC x64 + Windows SDK); install that, or run from a Developer
Command Prompt (LIB set). Bundling the libraries so no install is needed
is s47's (the s60 campaign).

Exit code 2, wrapped here and printed on one line there; wolf run says the same thing in the same words. It is a refusal before the link rather than a link error afterwards, which is the difference between a message that tells you what to install and a wall of unresolved symbols. Installing the workload is the whole fix. Shipping the import libraries inside the archive so that nothing has to be installed is planned work, and the refusal names it.

What still refuses

Three things a program can reach, and the compiler names each one to your face rather than building something that quietly is not what you asked for. (The ledger at the end of this section has the rest, none of which a first program meets.)

wolf build --release, the LLVM optimizing tier, refuses this host with exit code 2:

wolf build: this host cannot run the release tier: the release
tier targets linux/x86-64 and macOS/aarch64 (s41 + s127; c13 owns the
matrix) — this host is neither, and further platforms follow as their
own sprints

Wrapped here and printed on one line there. The plain wolf build is the one you want on Windows today, and it is a real native build: the same machine code through the compiler's own backend, without an LLVM pass pipeline over it.

External reload and upgrade signals have nothing on Windows to arrive through. The console offers Ctrl+C, Ctrl+Break and the window closing — which wolf reads as terminate and quit — and nothing at all that means "reload". Inside your own program every meaning works: the corpus's signal witness listens for reload, raises it, waits for it and prints reload, and the CI job runs that program on a Windows runner and reads exactly that back. What you cannot do is send one from another process, so a long-running program that wants reload or upgrade on this host takes them over a control channel instead.

Unix-domain sockets — net_listen_unix and net_connect_unix, which are new at __WOLF_VERSION__ — answer the unsupported row on this host. By name, rather than as a bare io failure: the difference is whether a program can branch on the host at all, and it is the whole reason the row exists. AF_UNIX has been in Windows since build 1803 and the compiler's own test suite measures the kernel's answer on a runner, but the runtime carries no winsock binding for the family, so the ledger names the rung instead of claiming it. A program that wants a local control endpoint here keeps it on loopback TCP. The job that measures this page runs the corpus's unix witness on a Windows box and reads the named row back from it.

Everything else the language has is here. Tasks and scopes, proc, channels and select, sync/ when, region transfer, os.signal and network deadlines all compile and run, alongside everything a first month of wolf touches — printing, strings, lists, JSON, files, environment and child processes, time, random, regions and the region ledger, and TCP sockets. The release records this host at macOS parity across the conformance corpus, with no row refused by construct name at all: the thirty-six rows the native lane does not execute here are exactly the thirty-six it does not execute on macOS, which makes them the lanes' own scope gaps rather than this host's. A stack overflow inside a task reports in wolf's own words — wolf-rt: stack overflow in task '…', exit 134 — while one in a program that never spawns still dies as a bare 0xC00000FD, because the reporter is installed when the task pool starts and a program with no tasks never starts one.

The compiler's own per-host ledger is docs/platforms.md at the release tag: the table of what each host serves, the refusals row by row, the linker order in full, and the named sprints that close the gaps — including two this page does not measure because no first program meets them, structs passed by value across the extern "c" boundary and the debugger.

Line endings

If you wrote hello.lu in Notepad, it has Windows line endings, and:

wolf fmt --check .\hello.lu
wolf fmt --check: ./hello.lu is not canonically formatted

Exit code 1. Canonical wolf source is LF, and wolf fmt hello.lu rewrites the file — line endings included — after which the check passes. The formatter has no options, so there is nothing to configure and nothing to argue about.

Two more verbs

wolf test hello.lu runs the program and reports a verdict instead of its output — test hello.lu::main ... ok, then 1 passed; 0 failed. It is the short way to ask whether a program still works.

wolf conform-run hello.lu --checked is also available, and it is a different thing: a conformance harness rather than a runner. It executes your program on the compiler's own checked machine — no code generation, no linker, so it works on a box with no Build Tools at all — and prints a one-line machine record instead of your output:

{"commit":"…","diagnostics":[],"file":"./hello.lu","impl":"wolfgang",
 "impl_version":"__WOLF_VERSION__","phase_reached":"run","protocol":1,
 "seeded":false,"stdout_inline":"hello, wolf\n","stdout_sha256":"…",
 "verdict":"exit(0)","warnings":[]}

Wrapped here; the build commit and the output digest are elided. Your program's output is the stdout_inline field. Drop --checked and it stops before code generation and answers "verdict":"unsupported". Through v0.2.1 this was the only way to run a program on Windows, and this page led with it; it is now the specialist's tool it was always meant to be.

The interpreter, and the playground

Wolf has a second implementation: lupin, a reference interpreter written against the same specification, sharing no code with the compiler. It is now published for Windows as a single file — lupin.exe, about 5 MB, no installer and nothing beside it. Running a file takes no subcommand:

lupin hello.lu
hello, wolf

It is a good second opinion when the compiler and your expectations disagree — a different implementation reading the same specification, not a fallback for what the backend cannot do. That distinction had to be won: through v0.2.2 lupin was also the only way to run a program on this host that used a task or a channel, and it has not been that since v0.2.3. lupin --version names the release and the specification pin it was built against, which is the pin the second line of wolf --version quotes back — the same pin as the compiler's at this release, as above.

The playground runs that same interpreter compiled to WebAssembly — lupin __LUPIN_VERSION__, in the tab, with the corpus programs to load, and nothing to download at all. Its editor is exercised on a Windows runner in this site's CI, in the Ctrl spelling a Windows browser sends rather than the Cmd one; the single Windows-specific catch is a hotkey some graphics drivers take before the browser sees it, and the playground page names it beside its key bindings.

Everywhere else

linux x86-64 and macOS aarch64 are the two hosts the whole toolchain is built and tested on: wolf run compiles to native machine code through the compiler's own backend and executes it, wolf build --release goes through LLVM, and the concurrency runtime is all there. Take the archive for your platform from the releases page and put its folder on your PATH — the binary and the runtime archive have to stay together, because the binary cannot link a program without it.

__WOLF_VERSION__ carries four archives, one for every tier-1 host: those two, windows x86-64, and linux aarch64. That last one has no native backend behind it yet, so what its archive serves is the checked tier — wolf test and wolf conform-run --checked run your program, wolf run refuses the host by name — and v0.2.2 shipped no arm archive at all, because the smoke that gates the upload could not tell an unserved host from a broken build. Every release since carries it. All four URLs are asked for a 200 by the same job that measures the Windows section, every time this site changes. For a host outside the matrix, the source recipe is the path.

The front page has the four lines that build the same toolchain from source, which is the path the project itself is known to work on.

The Windows facts on this page were measured on a Windows runner against the published archive, by a job that reruns weekly. If the page and the archive disagree, the archive is right and the job is about to say so.
